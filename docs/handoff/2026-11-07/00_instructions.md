## 4. 全程适用的规则

1. **不推送到 GitHub**，直到作者说可以。
2. **不删除任何分支，不改写历史。**
3. **已登记的判定（P1–P7、B33–B43）不改。** 新分析一律标为“探索性、事后提出”，运行前先登记。
4. **文件与仓库实际情况冲突时，以仓库为准**，并在汇报里写明冲突在哪里。例如：本包写的文件名或运行名与仓库里的不一致。
5. **不修改论文草稿。** 发现草稿有错，写进汇报。
6. **遇到以下情况，先停下来汇报，等作者决定：**
   - 一个不能撤销的操作，而且两种做法都说得通；
   - 第二阶段重跑的结果超出容差，并且找不到原因；
   - 需要购买或申请新的算力、数据或权限。
7. **遇到以下情况，继续做，但在汇报开头醒目标出：**
   - 第一阶段 X5 走了“版本 C”分支（可能改变论文叙事）；
   - 发现原代码的 bug。
